# BTCognitive V36.1 — Feature Value / Ablation Protocol

## Status

Preregister before any feature experiment. No feature selection, tuning, model training, or final-holdout access occurred in V36.1. Do not tune against frozen prospective records. All retrospective results remain development/replay evidence, not fresh confirmatory evidence.

## Hypothesis and frozen unit of analysis

For the trade-outcome track, one observation is an eligible candidate generated by the same frozen stage-one setup detector at a completed 15-minute decision time and resolved by the same frozen fill/barrier/outcome contract. Candidate origins, outcome rows, target horizon, exclusion reasons, and costs are identical across comparisons. For volatility forecasting, run a separate experiment on the exact variance target and forecast origins; do not merge its scores with the trade classifier or report direction.

Before splitting, freeze: data source/hash and cutoff; candidate detector; label resolver and collision policy; feature definitions/units/availability; model family; cost scenarios; metrics; fold schedule; purge/embargo; ablation list; subgroup definitions; multiplicity family; sample/effective-N rules; and stopping/promotion gates.

## Controlled comparisons

| Model block | Contents | Purpose |
|---|---|---|
| Baseline only | Frozen structural candidate generator plus preregistered intercept-only outcome model; separately report accept-all B3 utility if that is the declared baseline | Establish candidate base rate and baseline probability loss |
| Baseline + trend/momentum | Causal, preregistered return/EMA/channel features | Incremental trend information |
| Baseline + volatility | ATR/realized variance/semivariance features with same target horizon and no future leakage | Incremental scale/risk information |
| Baseline + regime | Frozen PIT state/regime features | Conditional value beyond baseline and other already included blocks |
| Baseline + microstructure | Actual timestamped L2/trade-event features only | Entry timing/execution value; unavailable on current Bitstamp snapshot |
| Supported combinations | Only groups with available, permissioned data; combinations preregistered before folds | Test conditional interactions without arbitrary bundle search |
| Full eligible set | Union of preregistered, available groups | Final ablation reference; no unavailable/synthetic features |

Candidate side, execution timing, candidate count, outcomes, and decision thresholds cannot vary across feature blocks. Fit every feature transform inside each chronological training fold. A missing source feature remains unavailable; do not use neutral values to make the full set appear complete.

## Walk-forward and leakage control

- Use expanding or rolling chronological training windows and fixed, non-overlapping evaluation blocks.
- Preserve a sealed final holdout and do not inspect it for feature screening, direction, threshold selection, calibration choice, or model selection.
- Purge any training candidate whose label path overlaps the evaluation block. Embargo at least the maximum label horizon plus next-bar fill delay and account for delayed source publication.
- Keep candidates from the same unresolved/overlapping episode together. Enforce the frozen one-open-position policy when constructing realized candidate sequences.
- Feature timestamp and availability checks are asserted against each decision time. Future-label builders are isolated from feature builders.
- Historical replay is retrospective; it does not count as untouched prospective confirmation. Protected prospective observations remain unavailable for tuning.

## Evaluation and diagnostics

For the three-class outcome model, primary scores are multiclass log loss and Brier score; report calibration by class, reliability, support, and confidence intervals. For variance forecasts, use a separately declared variance loss (including QLIKE where target assumptions hold). For execution utility, calculate net R under both frozen BASE and CONSERVATIVE costs, not hypothetical gross returns alone.

Report per fold and pooled (with correct dependence handling): candidate counts; exclusions by reason; label proportions; overlapping-label count; uniqueness/effective sample size; scores and paired feature-block loss differences; confidence intervals; cost sensitivity; candidate acceptance/abstention rate; volatility-regime summaries; missingness/availability coverage; and model/feature hashes.

Use paired block or cluster bootstrap consistent with the maximum horizon and candidate clustering. Use Diebold–Mariano with appropriate dependence correction, and Harvey–Leybourne–Newbold finite-sample correction with Student's `t_(T-1)` where its assumptions and sample definition apply. Correct the preregistered family of ablation comparisons with Holm–Bonferroni. State clearly where a test is inapplicable or effective sample is insufficient. Report conditional permutation within time/regime/volatility strata; do not arbitrarily shuffle serially dependent rows.

## Multiple testing and overfit controls

- Count every barrier pair, feature set, model family, threshold, cost scenario, subgroup, and sensitivity analysis in the search family.
- Freeze a limited comparison set. Do not expand feature combinations after seeing validation results without registering a new research cycle.
- Use nested chronological development folds for model/threshold selection; final holdout remains unopened until freeze.
- Report selection-adjusted results and all tried variants, not only the best.
- Treat PBO/DSR/White's Reality Check as supplemental only after independently validating implementation and assumptions. Existing helper names in `walk_forward_engine.py` are not evidence those methods are correctly implemented.
- No performance threshold is changed to obtain a pass; no prospective protocol is modified.

## Acceptance and no-go

An ablation is interpretable only if all blocks have the same valid origins, outcomes, horizon, costs, and exclusions; PIT/leakage checks pass; the effective sample is reported; multiplicity and serial dependence are addressed; and no holdout/prospective contamination occurred. If intervals are too broad or a class/fold lacks support, result is `INCONCLUSIVE`. A feature contributes only if its incremental benefit is stable, material under preregistered utility and calibration criteria, and survives corrected inference and regime/robustness checks. Otherwise retain baseline or mark feature contribution `NOT ESTABLISHED`.
