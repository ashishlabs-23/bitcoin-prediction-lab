# BTCognitive V36.3 — Frozen Contract Conformance

## Scope and status terms

Static inspection only; no tests, source execution, or data replay. The frozen specifications are in `PREREGISTRATION_v1.md`, `decision_contract.json`, `entry_execution_contract.json`, `outcome_accounting_contract.json`, and `instrument_contract.json`. The eight files listed by `contract_freeze_manifest.json::contract_file_hashes` still match their declared hashes. A matching frozen-contract hash proves the specification has not changed; it does not prove code conformance.

`CONFORMANT` means the inspected source behavior matches the specified requirement; `PARTIAL` means some behavior matches but an important branch is missing or conditional; `DEVIATION` means a static mismatch is visible; `UNVERIFIABLE` means source/data semantics or runtime evidence is insufficient; `OWNER DECISION` means the frozen wording itself needs clarification before a safe implementation choice.

## Conformance decision

The frozen contract files themselves are intact, but the currently inspected data-to-label implementation is **not contract-conformant** for exact entry timing, gap cancellation, gap-first touch ordering, exact path horizon, and cost accounting. Several issues cannot be resolved by editing the resolver alone: the timestamp role, decision-bar aggregation, short-spot eligibility, A1 confirmation behavior, cost representation, and gap tolerance need explicit decisions or admissible source evidence first.
